# Карта данных Nivel

Дата: 06.10.2026. Ведёт WP-06 (база данных). Основа — ARCHITECTURE 3 и 10.2; здесь только то, что построено в схеме: где лежат данные, кто их пишет и читает, какие из них персональные (ПД), сколько хранятся и чем защищены. Расхождения с разделом 3.3 архитектуры собраны в разделе 8.

## 1. Как читать

- Схемы PostgreSQL: `catalog`, `pricing`, `sales`, `content`, `ai`, `bot`, `ops`; очередь — `pgboss` (создаёт worker), аналитика Umami — отдельная база.
- «Пишет» — роль БД, у которой есть право на запись в таблицу. «Журнал» — триггер запрещает `UPDATE` и `DELETE`. «Неизменяема» — после создания или публикации строка не меняется.
- ПД: **да** — прямые данные человека (имя, телефон, Telegram, адрес, паспорт, e-mail); **косвенно** — хэши и ссылки, по которым человека можно найти только через другую таблицу; **нет**.
- Деньги — целые сумы (`bigint`), ставки — базисные пункты (`integer`); дробных типов в схеме нет (проверяется тестом).

## 2. Роли и права

| Роль | Что может | Чего не может |
| --- | --- | --- |
| `nivel_migrator` | DDL, миграции, сид, сброс; владелец функций `sales.apply_transition`, `ai.purge_expired`, `ops.next_number` | запускается только контейнером `migrate` и командами `pnpm db:*` |
| `nivel_web` | читает каталог, цены, контент, настройки; пишет `configurations`, `leads`, `customers` (создание), `ops.consents`, `ops.outbox`, `ops.audit_log` (только добавление), журнал ИИ; читает деньги заказа только через `sales.v_customer_order_*`; вызывает `apply_transition` только как `customer` | читать `sales.payments`, `sales.purchases`, `sales.orders`, `sales.quotes`; телефон, адрес и комментарий заявки; менять чужие записи; DDL |
| `nivel_admin` | всё в схемах приложения, кроме журналов (только добавление) и фиксированных строк | DDL; `UPDATE` и `DELETE` журналов; `DELETE` платежей и наблюдений цен; правка графа статусов |
| `nivel_bot` | заявки, клиенты, сессии, согласия, очередь; читает заказы, сметы, платежи, закупки, акты; вызывает `apply_transition` | писать платежи, закупки, сметы напрямую; читать `customer_secrets`, журнал ИИ |
| `nivel_worker` | цены, курсы, очередь, файлы, ошибки, срезы порога, резервы; читает продажи без адресов клиентов; вызывает `apply_transition` только как `system`; `ai.purge_expired()` | писать заказы и платежи; читать `customer_secrets` и адрес клиента; `DELETE` наблюдений цен |

Статус заказа не меняет никто, кроме функции `sales.apply_transition()`: прямой `UPDATE` отклоняет триггер (`direct_status_change`), даже если вызывающий выставил служебный флаг сам — флаг действует только внутри функции под владельцем.

## 4. Журналы и неизменяемые записи

| Что | Как защищено | Исключение |
| --- | --- | --- |
| `ops.audit_log`, `ops.consents`, `sales.order_events`, `sales.reserve_ledger` | триггер на `UPDATE`, `DELETE`, `TRUNCATE`; право `UPDATE`/`DELETE` у admin отозвано | нет |
| `ai.messages` | то же | удаление только через `ai.purge_expired()` (90 дней) |
| `pricing.price_observations` | `DELETE` и `TRUNCATE` запрещены | меняются только `excluded` и `exclude_reason`, парой |
| `sales.payments` | `DELETE` и `TRUNCATE` запрещены | `expected → confirmed \| void` и поля подтверждения |
| `sales.configurations` | любое изменение запрещено | нет |
| `sales.quotes`, `sales.quote_lines` | после `draft` строки заморожены | статус `sent → accepted \| expired \| superseded`, один раз `acceptance` и ссылки на PDF |
| `content.legal_documents` | опубликованная версия не меняется и не удаляется | нет |

## 5. Деньги: правила базы (вторая линия после `packages/domain`)

| Правило | Где | Сообщение или ограничение |
| --- | --- | --- |
| плата — QR с чеком; деньги на закупку — только перевод на счёт ИП; возвраты — только исходящий перевод | CHECK `payments_fee_chk`, `payments_purchase_funds_chk`, `payments_refund_chk` | `check_violation` |
| подтверждённый платёж имеет автора и время | CHECK `payments_confirmed_chk` | |
| знак суммы: платёж и закупка положительные, исправление и возврат магазину — отрицательные со ссылкой | CHECK `payments_amount_chk`, `purchases_amount_chk` | |
| закупки заказа ≤ лимита сметы, иначе нужно согласие `limit_overrun` (действует последняя запись) | триггер `purchases_guard` | `limit_exceeded` |
| закупки ≤ подтверждённых `purchase_funds + purchase_topup` (своими деньгами за клиента не платим) | триггер `purchases_guard` | `funds_exceeded` |
| закупка без чека — только с согласием `no_receipt_purchase` | триггер `purchases_guard` | `consent_missing` |
| `closed` и `cancelled`: полученные деньги = закупки + возвраты + документированные потери | триггер `orders_guard` | `not_reconciled` |
| у заказа есть текущая смета, и она его собственная | внешний ключ `(current_quote_id, id)` и `no_current_quote` | |
| аванс + остаток = плата; «вознаграждение» + «работы» = плата; резерв ≤ лимита закупки | CHECK `quotes_fee_split_chk`, `quotes_fee_lines_chk`, `quotes_limit_chk` | |
| помощник не вызывает денежные события; сайт действует только как клиент, worker — как система | `sales.apply_transition` | `actor_not_allowed` |

Одна таблица случаев: `packages/testing/fixtures/wp-06/db-money-cases.json` (пары платежей, лимит и деньги, сверка) прогоняется против реальной базы тестом `money-cases.suite.ts`. Общий `money-cases.json` из WP-01 подключит интегратор после слияния: форма та же.

## 6. Представления и функции

| Объект | Назначение |
| --- | --- |
| `pricing.v_market_price_current` | последняя рыночная цена каждой позиции (снимок конфигуратора одним запросом) |
| `sales.v_customer_order_status`, `_quotes`, `_payments`, `_purchases` | единственный путь сайта к деньгам и закупкам: без номеров банковских документов, сотрудников и без названий магазинов, не давших согласие на упоминание |
| `sales.v_deal_volume_by_year` | сделки года для порога: чеки закупок + полученная плата − возвращённая плата + доход другой деятельности ИП; год — по Ташкенту |
| `sales.apply_transition(...)` | единственный автор статуса: статус, событие журнала, запись аудита; защита от устаревшего статуса (`stale_status`), граф из `sales.order_transitions` |
| `ops.next_number(kind, year)` | `L-`, `NV-`, `G-` по годам, без пропусков внутри транзакции |
| `ops.consent_granted(order, kind)` | последнее согласие вида по заказу |
| `ai.purge_expired(now)` | удержание: диалоги ИИ старше срока |
| `catalog.spec_complete(category, specs)` | полнота ключей правил «нельзя» для статуса `verified` |

## 7. Сид и сброс

- Слой правил (можно в продакшене): категории, лестницы, классы цен, 32 шаблона блока 28, первый набор правил подбора, денежные настройки по умолчанию (Р-8), флаги функций выключены.
- Демо-слой (`is_demo`, отказ при `APP_MODE=production`): 53 позиции блока 28 с характеристиками для проверок совместимости, три демо-поставщика, наблюдения цен, медианы, курс 11 772,95, шесть витринных сборок, две демо-«идеи». У RTX 5070 два продавца (доверие `low`, без медианы), у памяти 128 ГБ — одна оценка.
- Команды: `node seed/cli.ts seed` (добавить к мигрированной базе) и `reset` (сбросить схемы, применить миграции с нуля, засеять). Только локальный хост и не продакшен. Подключение как `pnpm db:seed` и `pnpm db:reset` — заявка интегратору (раздел 9).
- Перед продажами: `pnpm check:demo` в режиме production не должен находить демо-строк, видимых клиентам.

## 8. Расхождения с ARCHITECTURE 3.3 (решения WP-06, нужны для архитектуры)

| Что | Решение | Причина |
| --- | --- | --- |
| `categories.group` | колонка `category_group` | `group` — зарезервированное слово SQL |
| `orders.documented_losses_sum` | новая колонка | в сверке 3.4 есть `documented_losses`, а места для него не было |
| `payments.reversal_of`, `purchases.refund_of` | исправление — строка со знаком минус | журнал не правится; суммы сверки учитывают минус сами |
| `perf_facts.published` | новая колонка | «без источника не публикуется» должно проверяться |
| `ops.outbox.last_error`, `sent_at` | новые колонки | повторы и разбор сбоев |
| `ops.number_counters`, `sales.order_transitions` | новые таблицы | номера без пропусков; граф статусов как данные |
| `ladders.steps` | `uuid[]`, по одному основному классу на ступень; равные ступени — через `price_classes.step` | порядок и альтернативы одного уровня |
| «2 + 2 ТБ» | две строки шаблона (`ssd.2tb` и `ssd.2tb_senior`) | отдельного класса для пары нет |
| `sales.v_customer_order_quotes` | пятое представление | клиент видит смету без внутренних полей |
| `products.returnable`, `fee_group` | `NULL` — взять из категории | переопределение, а не копия |

## 9. Допущения и открытые вопросы

- Характеристики демо-позиций — правдоподобные значения для проверок, не справочник; перед продажами каждую позицию вводит и проверяет владелец по странице производителя.
- Шаблоны «Дизайн Т4» и «Программирование Т4» содержат 128 ГБ памяти (по таблице блока 28), а 128 ГБ в том же блоке подбираются только вручную: класс `ram.ddr5_128` помечен `manual_only`, WP-05 нужно решить, как собирать эти две клетки.
- «Не предлагаем»: переход для «Стрим Т1» — задача «Игры», для «Офис Т2» — «Программирование», для «Офис Т3–Т4» — «Дизайн»; блок 28 называет пару «Программирование или Дизайн» без привязки к уровню.
- `returnable_default = true` у всех категорий, кроме лицензии Windows; правила возврата памяти и накопителей уточняет юрист вместе с офертой.
- Праздничный календарь в `ops.settings` (`calendar.work.holidays`) пуст до утверждения владельцем.
- Доли шаблона по стилям Б: белый блок питания, башенный кулер и радиатор Б, белая память 32 ГБ, корпус Б, три белых вентилятора с Т2 — по блоку 28, 1.1.
